# Architecture decisions

## Publishable key and RLS

The browser uses a public Supabase publishable key. This identifies the project, not a trusted user. Row Level Security limits updates/deletes to the owner, hides taken and expired listings from other people, and makes saved rows private. Profiles require an authenticated session. Never ship a service-role key. Public storage URLs can be viewed by anyone who knows the URL; hiding a profile card is not private-image storage.

## Email codes

Email one-time codes keep sign-in in the same tab and work with the GitHub Pages base path. Codes avoid magic-link redirects opening a different browser. The UI accepts 6–10 digits and validates return paths to reject external redirects. New users finish their profile before continuing to their requested destination.

## Server-side UW restriction

The Before User Created hook checks the email domain in Supabase. The form's wisc.edu check is only a friendly early error; it cannot enforce security. Enable the hook in the project dashboard and test it by bypassing the form. Existing auth users must also be audited when connecting an existing project, since a creation hook does not remove preexisting accounts.

## Column-level grants

RLS governs which rows a user can change. Column grants separately prevent changes to email, ownership, demo flags, IDs, and timestamps. A user-created building cannot provide an OSM footprint. Database checks enforce ranges, dates, amenities, room pricing, and the Madison bounding box.

## Storage folders and image preparation

Paths begin with the authenticated user's ID. Storage policies check that first folder for writes, replacements, reads through the API, and deletion. Listing photos use unique names below the listing ID, so retries and edits do not replace currently displayed photos. Canvas conversion caps the long edge at 1600px and exports WebP at 0.8 quality. Avatars use a centered 512px crop and a stable path with a timestamp URL for cache refresh. Uploads and database writes are not one transaction: incomplete new listings stay taken, form retries retain the ID, and cleanup can be retried separately.

## Client-side filtering

Browse fetches active listings and buildings once per mount, with explicit retry on failure, then filters and sorts in memory. This is simple at a campus-project scale. Supabase's configured maximum rows per request (commonly 1,000) is a hard boundary: before reaching it, use server-side filters, pagination, search indexes, and map aggregation. Do not silently treat a capped response as the full inventory. React StrictMode may issue duplicate development fetches during its mount checks.

## URL state

Search, rent, beds, baths, amenities, dates, unit type, sort, and building selection live in the query string. Reloads and shared links reproduce the search. Text and price changes are debounced. Clearing filters preserves sorting and the selected building; the building chip clears selection separately. The landmark is a localStorage preference rather than search criteria.

## OSM data

The existing seed coordinates and prefetched GeoJSON outlines come from OpenStreetMap. Runtime browsing does not call Overpass or a geocoder. Buildings without outlines use circle markers. New locations come only from a user's map pin constrained to the OSM-derived Madison bounds. Attribution remains visible.

## CARTO tiles and themes

Browse and the homepage draw local OSM building outlines and solid streets through CampusMap. The campus-area snapshot is generated by scripts/fetch-basemap.mjs; paths and labels are omitted to keep listing highlights prominent. It has finite coverage rather than worldwide tiles. The listing form retains detailed tiles: a CARTO key selects Positron/Dark Matter, otherwise OSM provides a fallback. CSS custom properties define interface and map colors. The initial theme follows the OS by default and remembers an explicit choice. Browse exposes the saved walk landmark in an always-visible map control; price pills appear only at zoom 18 and above.

## Accessible navigation

The listing list is the primary keyboard route through results; focus also highlights its building. Mobile filters and deletion use native modal dialogs to contain focus and return it on close. The mobile collapsed list is inert, while its handle and Filters button remain available. Photo controls have labels and arrow-key support. Reduced-motion preferences disable CSS transitions and map flights.

## UI refinement

The landing page and navigation use shadcn/ui Button/Card components adapted to JavaScript. Tailwind v4 builds their utilities without applying its reset to the existing forms and Leaflet map. The Lora serif is bundled locally for editorial headings; controls retain a system sans-serif. Soft gradients and a fine texture add depth, while one-time IntersectionObserver reveals and a small progressive-enhancement scroll effect respect reduced-motion preferences. UI credits are in UI-CREDITS.md.

The latest housing-themed design supersedes the gradient treatment above: original SVG linen and floorplan textures, Lora prose and headings, DM Sans UI labels, and a requestAnimationFrame scroll scene replace the earlier subtle CSS-only map motion. The desktop scene is short, mobile has no pinning, and reduced-motion removes it. DM Sans is licensed under the SIL Open Font License, included in public/licenses/dm-sans.txt.
